# lineage-matrix

VBA が全クエリそれぞれを起点として多階層の依存チェーンをフルに展開した
Access SQL（Jet-SQL、`chain_queries.json`）から、各クエリが参照しているテーブルを
テーブル単位で抽出し、クエリ階層×参照テーブルのマトリックス表を出力するツール。

**クエリ内の参照テーブル収集に特化したツール**（カラム単位のリネージ解析、
AI変換済みSQLの事前検証は対象外）。

テーブル参照の抽出だけであれば [SQLGlot](https://github.com/tobymao/sqlglot) は
関数の意味を理解する必要がなく構文的にパースできればよいため、AI変換・SSMA変換を
一切経由せず、Access SQL（Jet-SQL）をそのまま `find_all(exp.Table)` で走査する
（AI変換はボトルネックであり、SSMAは`Format`関数・パラメータクエリ・
クロスタブクエリを変換できないため）。

全クエリを個別に、代表クエリへの絞り込みや重複チェーンの除外なしにマトリックス表へ反映する
（クエリの類似度によるグルーピング・代表選出は行わない）。

## セットアップ

```bash
pip install -r requirements.txt
```

## 実行方法

```bash
python3 src/main.py
```

リポジトリルートから実行する（`input/`・`output/` は実行時の
カレントディレクトリ基準の相対パス）。
`input/table.json`（全テーブルの一覧）と `input/<起点クエリ名>/chain_queries.json`
（VBA出力のAccess SQL）を読み込み、起点クエリごとに `output/<起点クエリ名>/` へ
テーブル参照マトリクスを生成する。あわせて、全起点クエリ分の◎/○判定を1行1テーブル
参照の縦持ち形式でまとめた `output/matrix_long.csv` も出力する。

起点クエリは `input/` 直下の全サブフォルダから **自動検出** される。設定ファイルは不要。

テーブル参照の抽出結果だけを個別ファイルで確認したい場合は、`main.py`と同じ解析ロジック
（`table_reference_extract.classify_queries()`）を共有する単体コマンドも使える
（詳細は後述）。

```bash
python3 src/table_reference_extract.py
```

## `input/` のインターフェース仕様

```
input/
├── table.json                  # 全テーブルのフラットな一覧（VBAが出力）
├── クエリ工事委託分析/
│   └── chain_queries.json     # VBA出力（多階層フル展開済み、Access SQL）
└── クエリ入札委託集計分析/
    └── chain_queries.json
```

**起点クエリは自動検出される**：`input/` 直下の全サブフォルダのうち、
`chain_queries.json` が存在するサブフォルダ名が起点クエリとして自動的に認識される
（`input/table.json`はファイルなので対象外）。設定ファイル（`start_queries.json` など）は不要。

### 運用フロー

1. **VBA実行**: 全クエリそれぞれを起点として、多階層の依存チェーンを重複除外なしにフル展開
   → `input/<起点クエリ名>/chain_queries.json` 出力
2. **実行**: `python3 src/main.py` → 自動検出・テーブル参照抽出・マトリックス構築 → 結果出力

AI変換・SSMA変換のステップは不要。VBA出力のAccess SQLをそのまま解析する。

### `chain_queries.json`（VBA出力のAccess SQLのフラット一覧）

```json
[
  { "クエリ名": "クエリ工事基本",   "SQL": "SELECT A.[工事ID], A.[工事名称] FROM 工事台帳 A", "呼び出し元": [] },
  { "クエリ名": "クエリ工事集計",   "SQL": "SELECT [工事ID], [工事名称] FROM クエリ工事基本", "呼び出し元": ["クエリ工事基本"] }
]
```

| フィールド | 型 | 内容 |
|---|---|---|
| `クエリ名` | string | Accessクエリ名。`src/loader.py` の `load_queries()` がこれをキーとして辞書化する。 |
| `SQL` | string | Access SQL（Jet-SQL）のまま。変換不要。`IIf`/`Nz`/`Format`/`PARAMETERS ...;`/`TRANSFORM ... PIVOT ...` 等のAccess固有構文がそのまま含まれていてよい（後述の`normalize_jet_sql()`・`extract_referenced_tables()`が扱う）。 |
| `呼び出し元` | array | VBA側のチェーン検出の記録用フィールド。ツール側では使わない。 |

**クエリ間参照はそのまま**：`FROM クエリ工事基本` のようにクエリ名で参照する。
`classify_queries()` がそのグループ内の登録済みクエリ名一覧と突き合わせて解決する。

### `input/table.json`（テーブル情報・全件フラット）

物理テーブルの一覧。`src/loader.py` の `load_table_info()` が「物理テーブル名」の
組み立てに使う `物理名`・`スキーマ`（`スキーマ取得方法`とあわせて）を読み込む。
`テーブル名` は Jet-SQL側の参照名と突き合わせる際のキーとして使われる
（`table_reference_extract.classify_queries()` の `known_tables`）。

```json
[
  {
    "テーブル名": "工事台帳",
    "種別": "ローカルテーブル",
    "接続先": "",
    "物理名": "工事台帳",
    "スキーマ": "PO",
    "スキーマ取得方法": "ODBCリンクテーブル定義から自動取得"
  },
  {
    "テーブル名": "機関マスタ",
    "種別": "リンクテーブル",
    "接続先": "C:\\DB\\名称.accdb",
    "物理名": "機関マスタ"
  }
]
```

| フィールド | 型 | 内容 |
|---|---|---|
| `テーブル名` | string | Accessクエリ上で参照される論理名。`classify_queries()` の既知テーブル名一覧のキーになる。 |
| `種別` | string | 「ローカルテーブル」／「リンクテーブル」等。メタデータとして保持（読み込まれるが未使用）。 |
| `接続先` | string | リンクテーブルの接続先ファイルパス等。メタデータとして保持（読み込まれるが未使用）。 |
| `物理名` | string | 接続先における実際のオブジェクト名。「テーブル参照マトリクス」シートの「テーブル名」列（後述）の組み立てに使用する。 |
| `スキーマ` | string（省略可） | 物理テーブルのスキーマ名。省略時は空文字扱いとなり、物理テーブル名は`物理名`のみになる。 |
| `スキーマ取得方法` | string（省略可） | スキーマ名の取得方法（例：ODBCリンクテーブル定義から自動取得）。メタデータとして保持（読み込まれるが未使用）。 |

カラム定義（`カラム`フィールド）はカラム単位のリネージ解析が対象外になったことに伴い、
現在のパイプラインでは一切読み込まない。VBA側の出力に含まれていても無視される。

**物理テーブル名の組み立て**（`src/loader.py` の `build_physical_table_name()`）：
`スキーマ`が存在する場合は `スキーマ.物理名`（例：`PO.工事台帳`）、存在しない場合は `物理名` のみ。
「テーブル参照マトリクス」シートの「テーブル名」列（後述）はこの形式で表示される。

## 出力：`output/<起点クエリ名>/`

フォルダごとに以下の2ファイルを生成する。

### `lineage.xlsx`

「テーブル参照マトリクス」1シートのみを持つブック。`matrix_rows`
（`table_usage.resolve_table_usage()` が求めたdirect/indirect）から生成される
ビューであり、別ロジックで再計算されたものではない。

#### シート「テーブル参照マトリクス」

クエリ階層×参照テーブルの1行1テーブル参照の縦持ち形式。行は起点クエリから呼び出し可能な各クエリ（登録済みクエリのみ。ローカルな無名サブクエリは含まない）×参照している物理テーブルの組み合わせで、同じクエリが複数の親から呼び出されている場合は呼び出し元ごとに別行になる。`XLOOKUP`等のExcel数式で最終的な横持ちマトリックス表（開始クエリ／サブクエリ1／サブクエリ2／…に続けて、テーブルごとに個別の列。7/13決定のフォーマット）の各セルにマークを差し込む用途を想定した形式。

| 列名 | 内容 |
|---|---|
| 開始クエリ, サブクエリ1, サブクエリ2, ... | その行のクエリの、起点クエリからのパンくず（外側→内側）。列数はそのフォルダ内の最大ネスト数に応じて動的に決まる。自分自身の名前は自分の深さの列に入り、それより内側の列は空欄。 |
| テーブル名 | 参照している物理テーブル名（`table.json`の`スキーマ`・`物理名`から組み立てた形式。`build_physical_table_name()`、前述）。 |
| マーク | `○`（直接参照）または`◎`（間接参照）のいずれか1文字。 |

「マーク」列の`○`/`◎`の意味：

- `○`：その行のクエリが、自分自身のSQL（FROM/JOIN/WHERE/GROUP BY/HAVING/ORDER BYのいずれでも）で直接参照している物理テーブル
- `◎`：その行のクエリ自身は直接参照していないが、呼び出しているサブクエリ（の、さらに下位のサブクエリ…）を辿ると参照しているテーブル。開始クエリ、および間に挟まる上位のサブクエリすべてに付く

○/◎の判定自体はPython側（`table_usage.py` / `matrix.py`）で確定させた値であり、Excelの数式では計算し直さない。列構成は`output/matrix_long.csv`（後述）と同じだが、こちらはこのグループ（`lineage.xlsx`が属するフォルダ）の行のみを持つ。

### `error.json`

処理中に検知したエラー・警告の配列（構造化ログ）。エラーがなければ `[]`。

```json
[
  {
    "クエリ": "クエリL",
    "種別": "未解決テーブル参照",
    "メッセージ": "テーブル・登録済みクエリのいずれにも一致しない参照: 存在しないテーブル"
  }
]
```

`種別` は以下のいずれか。

- `パース失敗`：`normalize_jet_sql()`によるJet-SQL特有構文の除去後も`sqlglot.parse_one()`が例外を送出した（クエリ単位で処理を打ち切り、他のクエリの処理は継続する）
- `未解決テーブル参照`：参照名が`table.json`（既知テーブル）にもそのグループ内の登録済みクエリ名にも一致しなかった（目視確認の対象。テーブル名の表記揺れ・チェーン検出漏れ等が疑われる）
- `循環参照警告`：`table_usage.py`/`matrix.py`がクエリの呼び出しグラフを辿る際に循環を検出（通常のAccessクエリのチェーンでは起きない想定の異常系。検出した経路の探索はそこで打ち切り、他のクエリの処理は継続する）

## 出力：`output/matrix_long.csv`

全起点クエリ分の◎/○判定を1つにまとめた、1行1テーブル参照の縦持ち（ロング）形式のCSV。
`lineage.xlsx`の「テーブル参照マトリクス」シートと同じ列構成・同じ判定ロジック
（`table_usage.py`の direct/indirect）だが、こちらは全起点クエリ分を1ファイルに
集約したもの。`XLOOKUP`等のExcel数式で最終的な横持ちマトリックス表（開始クエリ／
サブクエリ1／サブクエリ2／…に続けて、テーブルごとに個別の列。7/13決定のフォーマット）
の各セルにマークを差し込む用途を想定している。

| 列名 | 内容 |
|---|---|
| 開始クエリ, サブクエリ1, サブクエリ2, ... | 「テーブル参照マトリクス」シートと同じパンくず列。列数は**全起点クエリを横断した**最大ネスト数に揃えられる（1ファイルにまとめるため、あるグループの列数が他のグループより浅い場合は余った列が空欄になる）。 |
| テーブル名 | 参照している物理テーブル名（`table.json`の`スキーマ`・`物理名`から組み立てた形式。「テーブル参照マトリクス」シートの物理テーブル名と同じ）。 |
| マーク | `○`（直接参照）または`◎`（間接参照）のいずれか1文字。同一の開始クエリ・サブクエリ階層・テーブル名の組み合わせに対して必ず1つ（directとindirectは互いに排他のため重複しない）。 |

```csv
開始クエリ,サブクエリ1,テーブル名,マーク
クエリ業者入札集計,,入札明細台帳,◎
クエリ業者入札集計,,業者台帳,◎
クエリ業者入札集計,クエリ業者入札明細,入札明細台帳,○
クエリ業者入札集計,クエリ業者入札明細,業者台帳,○
```

Excelで文字化けしないよう、UTF-8 with BOM（`utf-8-sig`）で出力する。
`error.json`とは異なりグループごとのファイルではなく、`main()`が`process_group()`から
返る縦持ちレコードを全起点クエリ分集約したうえで、`output/`直下に1ファイルとして出力する
（`table_reference_extract.py`の`output/table_references.json`と同じ
「全起点クエリ分をまとめて1ファイル」の考え方）。

## テーブル参照抽出：`table_reference_extract.py`

`chain_queries.json`（Access SQL/Jet-SQL）からクエリが参照するテーブルの一覧を
テーブル単位で抽出する、lineage-matrix唯一の解析経路。`main.py`（マトリックス表の構築）
と `table_reference_extract.main()`（`output/table_references.json`単体出力）の
両方がここを共通で使う。

Jet-SQL特有の以下2構文だけを正規表現で前処理して除去してから
`sqlglot.parse_one(sql, read="tsql")` でパースする（`tsql`はJet-SQL自体の方言が
sqlglotに存在しないため、構文的に近いものとして採用。関数の意味解釈は不要なため
`IIf`/`Nz`/`Format`等はそのまま残してよい）。

- 先頭の `PARAMETERS ... ;` 宣言
- `TRANSFORM <式> SELECT ... PIVOT <式>` のクロスタブ構文（`TRANSFORM`句と`PIVOT`句を除去し、中間の`SELECT ... FROM ... GROUP BY ...`部分のみ残す）

パースした結果 `find_all(exp.Table)` で取得した各テーブル名を、`table.json`由来の
テーブル名一覧・そのクエリグループ内の登録済みクエリ名一覧と突き合わせて分類する
（`extract_referenced_tables()`）。`classify_queries()` はこれをグループ内の
全クエリに対してまとめて実行するヘルパー。

`output/table_references.json` は全起点クエリ分をまとめた1ファイル：

```json
[
  {
    "クエリ名": "Q_Test_Crosstab",
    "参照テーブル": ["T_受注明細"],
    "参照サブクエリ": [],
    "未解決": [],
    "パース失敗": false
  }
]
```

- `参照テーブル`：`table.json`に存在する物理テーブルへの参照
- `参照サブクエリ`：他の登録済みクエリへの参照（VBA側のチェーン検出で既に捕捉されている想定のため、`参照テーブル`には含めない）
- `未解決`：テーブル・クエリのどちらにも一致しない参照名（目視確認の対象）
- `パース失敗`：前処理後もsqlglotがパースできなかった場合。他のクエリの処理は止めない

## `src/` のモジュール構成

```
src/
├── main.py                    # エントリポイント：起点クエリの発見、マトリクス構築、output/matrix_long.csvの集約出力
├── table_reference_extract.py # Jet-SQLからのテーブル参照抽出（main.pyと共有する唯一の解析経路）・単体実行時はoutput/table_references.jsonを出力
├── config.py                  # パス関連の定数、起点クエリ（input/配下のフォルダ）の発見
├── loader.py                  # input/*.json（クエリ）・input/table.json（全テーブル・物理テーブル名）の読み込み
├── table_usage.py             # classify_queries()が求めたdirect/childrenから、間接参照テーブルをボトムアップに積み上げる純粋なグラフ伝播（sqlglotに依存しない）
├── matrix.py                  # クエリ呼び出し木を辿り、クエリ階層×参照物理テーブル名のマトリックス（○/◎）を1行1テーブル参照の縦持ち形式で組み立てる
└── report.py                  # DataFrame化とファイル出力（Excel / JSON）
```

`src/` に `__init__.py` は置いていない。`python3 src/main.py` として直接実行する前提で、
各モジュールはスクリプトと同じディレクトリにある兄弟モジュールとして素朴に import している
（Pythonが実行スクリプトのディレクトリを自動的に `sys.path` に加えるため、パッケージ化は不要）。

`input/` 直下に起点クエリのフォルダが1件も見つからない場合、`main()` は
エラーメッセージを表示して終了コード1で終了する。
