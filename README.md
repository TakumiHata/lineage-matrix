# lineage-matrix

Accessクエリを SQL Server 用 SQL に変換した後の SQL 群を解析し、各クエリの出力カラムが
どのテーブル・カラムに由来するかをフラットテーブル形式で Excel 出力するツール。

カラムの由来解決には [SQLGlot](https://github.com/tobymao/sqlglot) の `lineage()` を使用し、
サブクエリ・CTE・集計関数（SUM等）を含む複雑な構造にも対応する。

## セットアップ

```bash
pip install -r requirements.txt
```

## 実行方法

```bash
python3 main.py
```

`input/` 配下のJSONを読み込み、`output/lineage.xlsx` を生成する。

---

## `input/` のインターフェース仕様

VBA側から出力される2つのJSONファイルを入力とする。この2ファイル以外は参照しない。

### `input/query_dependencies.json`（クエリ一覧）

Accessの各クエリと、SQL Server用に変換済みのSQL本文を並べた配列。

```json
[
  {
    "クエリ名": "クエリMain",
    "起点クエリ": "クエリMain",
    "親クエリ": null,
    "SQL": "SELECT ..."
  },
  {
    "クエリ名": "クエリ工事集計",
    "起点クエリ": "クエリMain",
    "親クエリ": "クエリMain",
    "SQL": "SELECT ..."
  }
]
```

| フィールド | 型 | 内容 |
|---|---|---|
| `クエリ名` | string | Accessクエリ名。`main.py` はこれをキーとして辞書化する（`load_queries()`）。 |
| `起点クエリ` | string | この連鎖の一番外側（最終的にユーザーが実行する）クエリ名。現状の `main.py` では未使用（メタデータとして保持のみ）。 |
| `親クエリ` | string \| null | このクエリをFROM句で参照している親クエリ名。独立クエリ、または連鎖の最上位クエリは `null`。現状の `main.py` では未使用（メタデータとして保持のみ）。 |
| `SQL` | string | SQL Server用に変換済みの、**そのクエリ単体で完結したSQL文字列**（tsqlダイアレクトでパース）。 |

**重要な制約**：`main.py` は各エントリの `SQL` を独立したスタンドアロンSQLとしてそのまま `sqlglot.lineage()` に渡す。あるクエリが別のクエリをFROM句で参照する場合（`親クエリ` が設定されている場合）でも、**参照先クエリのSELECT文がその場でサブクエリとしてインライン展開された完全なSQLになっている必要がある**。`親クエリ` フィールド自体を使ってSQLを跨いで解決するような処理は行っていない。

例えば「クエリ工事集計」が「クエリ工事基本」をFROM句で参照している場合、`SQL` フィールドには次のように、参照先の中身をそのままサブクエリとして埋め込んだ形で渡す必要がある。

```sql
SELECT [工事ID], [工事名称], SUM([発注金額]) AS [発注合計]
FROM (
    SELECT A.[工事ID], A.[工事名称], B.[発注金額]
    FROM [工事台帳] A
    JOIN [発注台帳] B ON A.[工事ID] = B.[工事ID]
) AS クエリ工事基本
GROUP BY [工事ID], [工事名称]
```

このとき、サブクエリのエイリアス名（`AS クエリ工事基本` の部分）を実際の参照先クエリ名と一致させておくと、出力される `output/lineage.xlsx` の「参照クエリ」列にそのクエリ名が現れる（`_walk_leaves()` が `reference_node_name` を辿って組み立てるため）。エイリアス名と実際のFROM句が一致していない場合、`sqlglot` はカラムの由来を解決できず「不明」として出力される（`main.py` 開発中に実際に踏んだ不具合であり、AI変換時の典型的な事故パターンなので特に注意）。

### `input/query_tables.json`（テーブル情報）

物理テーブルのカラム定義一覧。`sqlglot.lineage()` に渡すスキーマ辞書（`load_schema()`）の元データ。

```json
[
  {
    "テーブル名": "工事台帳",
    "カラム": [
      { "名前": "工事ID",   "型": "int" },
      { "名前": "工事名称", "型": "varchar" }
    ]
  }
]
```

| フィールド | 型 | 内容 |
|---|---|---|
| `テーブル名` | string | 物理テーブル名。`lineage()` のスキーマ辞書のキーになる。 |
| `カラム` | array | そのテーブルが持つカラムの配列。 |
| `カラム[].名前` | string | カラム名。 |
| `カラム[].型` | string（省略可） | カラムの型。**省略時は `"text"` として扱われる**（`load_schema()` の `col.get("型", "text")`）。型の値自体は突合には使われず、`lineage()` に「このテーブルにこのカラムが存在する」ことを伝えるためだけに使われる。 |

**注意点（大文字小文字）**：T-SQLは識別子の大文字小文字を区別しないため、`lineage()` がスキーマを解決する際に、ASCII文字を含むカラム名（例：`工事ID`）が内部的に小文字化される（`工事id`）ことがある。`main.py` はこれを検知し、`query_tables.json` に定義された表記に復元してから出力する（`_restore_schema_casing()`）。そのため `query_tables.json` に書かれたカラム名の大文字小文字が、そのまま `lineage.xlsx` の「参照カラム」列の正となる。

## 出力：`output/lineage.xlsx`

`input/query_dependencies.json` の各クエリについて、SELECTの出力カラムごとに1行、以下5列のフラットテーブルを出力する（列順もこの通り）。

| 列名 | 内容 |
|---|---|
| 開始クエリ | `クエリ名`（SQL自体をパースした対象クエリ） |
| 最終出力カラム | 開始クエリのSELECTで実際に出力されるカラム名（集計・エイリアス後の名前） |
| 参照クエリ | 出力カラムの由来を辿る過程で**最初に経由した**（一番外側で直接参照している）サブクエリ／CTEのエイリアス名。直接参照の場合は「（直接）」。2階層以上ネストしている場合でも、内側の中間クエリ名は記録されず一番外側の1つのみが残る。 |
| 参照テーブル | 最終的に辿り着いた物理テーブル名。解決できない場合は「不明」 |
| 参照カラム | 参照テーブル上の実際のカラム名。解決できない場合は「不明」 |

`lineage()` の呼び出し自体が例外を送出した場合は、参照クエリに「解析失敗」、参照テーブル・参照カラムに「不明」を記録し、最終出力カラムにエラー内容を併記した上で処理を継続する（1クエリの解析失敗が他のクエリの処理を止めないようにするため）。

## ディレクトリ構成

```
.
├── main.py                          # 解析・出力スクリプト
├── input/
│   ├── query_dependencies.json      # クエリ一覧（VBAスクリプト①が出力）
│   └── query_tables.json            # テーブル情報（VBAスクリプト②が出力予定）
├── output/
│   └── lineage.xlsx                 # 生成される成果物（git管理外）
└── requirements.txt
```
